1. PostgreSQL/PostGIS local avec Docker

Objectif :
- Fournir une base PostgreSQL locale de developpement avec PostGIS pour appliquer la migration initiale.

Etat verifie le 25/11/2026 :

- [x] Docker Compose a demarre le conteneur de base de donnees.
- [x] Le premier demarrage a pris du temps et s'est termine par une recuperation PostgreSQL interrompue.
- [x] Un redemarrage non destructif a permis a PostgreSQL de terminer la recuperation.
- [x] Le conteneur est maintenant indique healthy par Docker Compose.
- [x] PostgreSQL 16.4 repond sur le port local 5432.
- [x] PostGIS 3.4 est actif dans la base hydroalert.
- [x] La migration Prisma du projet est appliquee.

Pourquoi Docker Desktop convient :

- Docker Desktop lance PostgreSQL dans un conteneur, separement du backend.
- L'image postgis/postgis fournit PostgreSQL 16 avec l'extension PostGIS necessaire au schema.
- pgAdmin est facultatif : Docker Compose et la commande psql permettent de demarrer et verifier la base.
- Le port est publie uniquement sur 127.0.0.1 ; la base n'est pas exposee aux autres machines du reseau.
- Le volume postgres_data conserve les donnees lorsque le conteneur est arrete ou recree.
- Le mot de passe par defaut du compose est hydroalert et convient uniquement au developpement local. Ne jamais reutiliser cette valeur en production.

1.1 Demarrer Docker Desktop

- Cette etape est terminee : Docker Desktop et son moteur sont disponibles.
- Si Docker Desktop est arrete lors d'une prochaine session, le relancer avant de continuer.

1.2 Demarrer le service PostgreSQL/PostGIS

- Executer a la racine du projet :
	* docker compose up -d db
- La premiere execution peut telecharger l'image et prendre quelques minutes.
- Verifier l'etat avec :
	* docker compose ps
- Attendre que le service db soit indique comme healthy.
- Le premier demarrage a ici necessite un redemarrage : PostgreSQL avait ete interrompu durant son initialisation et a effectue une recuperation du volume.
- Le redemarrage simple docker compose up -d db a conserve le volume et a permis a la recuperation de se terminer ; ne pas supprimer le volume.
- En cas d'erreur indiquant que le port 5432 est occupe, ne pas supprimer de conteneur ni de volume ; signaler le message pour choisir un autre port de facon coherente.

1.3 Verifier que le port local est accessible

- Cette verification est terminee : Test-NetConnection retourne True et docker compose ps affiche healthy.
- PostGIS a egalement ete verifie avec docker compose exec -T db psql -U hydroalert -d hydroalert -tAc "SELECT postgis_version();".

1.4 Verifier la configuration locale sans partager les secrets

- Le fichier .env actuel doit contenir DATABASE_URL pour la base locale hydroalert sur 127.0.0.1:5432, et TEST_DATABASE_URL pour la base hydroalert_test.
- Utiliser 127.0.0.1 et non localhost : sous Windows, localhost resout d'abord en IPv6 (::1), alors que le port Docker n'est publie qu'en IPv4. Prisma renvoyait alors P1001.
- La configuration .env.example correspond au compose local avec l'utilisateur hydroalert et la base hydroalert.
- Ne pas coller le contenu du fichier .env dans le chat et ne pas le committer.
- Si POSTGRES_PASSWORD est defini manuellement dans .env, il doit correspondre au mot de passe utilise dans DATABASE_URL.
- Si .env contient des identifiants differents, ne pas les envoyer ; demander a l'assistant de verifier uniquement si la configuration est coherente.

Commandes courantes :
- pnpm dev : lance l'API (http://127.0.0.1:3000, documentation sur /docs).
- pnpm db:seed : recharge les donnees fictives sans doublon.
- pnpm test : tests sans base de donnees.
- pnpm test:integration : migre et remplit hydroalert_test, puis lance les tests d'integration.
- La base de test a ete creee une fois avec : docker compose exec db createdb -U hydroalert hydroalert_test
- pnpm docs:api : genere docs/API_HydrOAlerte_CI_v<version>.docx, la documentation API a transmettre aux responsables web et mobile.
	* Le document est produit a partir du code ; ne pas le modifier a la main.
	* A chaque changement d'API : incrementer info.version dans src/plugins/swagger.ts, ajouter une ligne a VERSION_HISTORY dans scripts/export-api-docx.ts, regenerer, puis committer le nouveau .docx.
	* Avec pnpm dev lance, la meme documentation est consultable sur http://127.0.0.1:3000/docs (interactive) et http://127.0.0.1:3000/docs/json (JSON brut).

Rendre l'API accessible aux autres modules :

- Les variables NODE_ENV, PORT, HOST, API_PUBLIC_URL et CORS_ORIGINS sont decrites dans .env.example. Absentes de .env, elles prennent leur valeur par defaut (port 3000, adresse http://127.0.0.1:3000, CORS ouvert a toutes les origines).
- 127.0.0.1 designe toujours la machine elle-meme : cette adresse ne fonctionne pas depuis le PC ou le telephone d'un coequipier.
- Test sur le meme Wi-Fi :
	* Trouver l'IP locale du PC avec ipconfig (ligne « Adresse IPv4 », par exemple 192.168.1.25).
	* Dans .env, mettre API_PUBLIC_URL=http://192.168.1.25:3000, puis relancer pnpm dev.
	* Autoriser le port 3000 dans le pare-feu Windows, une seule fois, dans PowerShell en administrateur :
		New-NetFirewallRule -DisplayName "HydroAlert API 3000" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow -Profile Private
	* Le reseau Wi-Fi doit etre en profil « Prive » dans Windows.
	* Les coequipiers utilisent alors http://192.168.1.25:3000. Le PC doit rester allume et l'API lancee.
- Emulateur Android sur le meme PC que l'API : utiliser http://10.0.2.2:3000.
- Sites web : le navigateur exige l'autorisation CORS. Ajouter l'origine du site dans CORS_ORIGINS (obligatoire en production, ou « * » n'est pas accepte par defaut). Les applications mobiles et les services IA ou IoT ne sont pas concernes.
- Apres tout changement de API_PUBLIC_URL, relancer pnpm docs:api pour que le .docx affiche la bonne adresse.

Rappel des regles et commandes de reference ci-dessous.

Preconditions :
- Etre dans C:\xampp\htdocs\hydroalert-ci.
- Avoir Docker Desktop demarre et le conteneur db indique healthy par Docker Compose.
- Avoir verifie localement DATABASE_URL sans la partager.
- Le conteneur db Docker doit etre indique healthy et PostGIS doit repondre.
- Ne jamais utiliser pnpm db:migrate:dev sur une base de production ou une base contenant des donnees a conserver.

Commandes a executer dans PowerShell, une par une :

- pnpm db:generate
	* Genere le client Prisma a partir de prisma/schema.prisma.
- pnpm db:migrate:dev
	* Applique la migration initiale a la base de developpement.
	* La migration active PostGIS et cree les tables du coeur : zones, sensors, measurements, predictions et alerts.
- pnpm db:migrate:status
	* Verifie que toutes les migrations du projet sont appliquees.
- pnpm test
	* Lance les tests automatises du backend.
- pnpm exec tsc --noEmit
	* Verifie les types TypeScript sans generer de fichiers.

Verification complementaire sans pgAdmin :

- Verifier que PostGIS est active :
	* docker compose exec db psql -U hydroalert -d hydroalert -c "SELECT extname FROM pg_extension WHERE extname = 'postgis';"
- Verifier la presence des tables du coeur :
	* docker compose exec db psql -U hydroalert -d hydroalert -c "SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' AND table_name IN ('zones', 'sensors', 'measurements', 'predictions', 'alerts') ORDER BY table_name;"
- Les deux requetes doivent retourner PostGIS et les cinq tables attendues.
- Avant la migration, la premiere requete doit retourner PostGIS ; les tables apparaitront apres pnpm db:migrate:dev.

Arreter PostgreSQL lorsque le projet n'en a plus besoin :

- Executer docker compose stop db.
- Pour le redemarrer, executer docker compose start db.
- Ne pas executer docker compose down -v : l'option -v supprime le volume et les donnees de la base.

Si une commande echoue :

- P1001 ou connexion refusee : verifier Docker Desktop, docker compose ps, l'hote et le port PostgreSQL.
- P1000 ou authentification refusee : verifier localement le nom d'utilisateur et le mot de passe dans .env.
- Erreur de permission PostGIS : copier uniquement le message d'erreur, sans URL ni identifiants, et demander de l'aide avant toute commande SQL manuelle.
- Erreur indiquant que la base n'est pas vide ou contient un schema inconnu : arreter et ne pas supprimer ni reinitialiser la base.

Compte rendu a envoyer apres l'action :

- Dire si le serveur PostgreSQL est joignable.
- Dire si Docker Compose indique le conteneur db comme healthy.
- Indiquer si pnpm db:migrate:dev a reussi.
- Copier les messages d'erreur eventuels apres avoir retire tout secret.
- Ne jamais envoyer DATABASE_URL, le mot de passe, le contenu de .env ou une capture qui les montre.
